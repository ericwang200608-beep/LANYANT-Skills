# Sync Mode: Propagate Principles into Dependent Artifacts

Use only when the user asks to propagate amended principles into the project's own dependent templates, command or skill files, and guidance docs. Without that request, the scope guard in [SKILL.md](../SKILL.md#scope-guard) holds and nothing outside the principles file is edited.

## What you are opting into

Propagation copies guidance out of the principles file into other files. That duplicates the source of truth: copies drift when the principles are amended again and propagation is not rerun. The default model, where design, planning, and verification read the live principles file every run, has nothing to re-sync and therefore nothing to drift. Propagate only when the team treats the materialized files as reviewed, committed artifacts (for example a plan template's principles check read in reviews as "here are our current gates").

## Scope while syncing

This section supersedes the scope guard's "dependent templates are not modified here" for propagation into the project's own dependent files. Every other scope-guard constraint still applies: do not implement features, generate application code, or touch artifacts unrelated to the principles and template workflow.

## Procedure

Run full-mode steps 1 to 8 first. Then, after the principles file is written, perform a consistency propagation pass:

1. Read the project's plan template (if it has one) and make any principles-check section or rules align with the updated principles. Materialize concrete gate text only if the team intends to review it as committed content; otherwise leave a pointer such as `[Gates determined based on the principles file]` so [technical-design](../../technical-design/SKILL.md) fills it from the live principles.
2. Read the project's specification template for scope and requirements alignment. Update it if the principles add or remove mandatory sections or constraints.
3. Read the project's tasks template and make task categorization reflect new or removed principle-driven task types (for example observability, versioning, testing discipline).
4. Read each project-local command or skill file that cites the principles (for example under `.claude/skills/`, `.codex/skills/`, `.github/skills/`, the harness's project-local rules directory) and verify no outdated references remain, including harness-specific names where generic guidance is required. **Hand-edit a file only if it is a project-local file not managed by a package, preset, plugin, or generator.** Files composed or regenerated by a tool must be regenerated through that tool; do not edit them in place, because the next regeneration clobbers the edits. List them as pending instead.
5. Read runtime guidance docs (for example `README.md`, `docs/quickstart.md`, `AGENTS.md`, `CLAUDE.md`) and update references to principles that changed.

Then extend the Sync Impact Report at the top of the principles file with:

- Templates and files requiring updates, each marked `updated` or `pending`, with file paths.

**Do not edit versioned, package-provided templates or command files directly.** They are owned by their packages and are recomposed on the package's next update; hand edits are clobbered. Limit propagation to the project's own scaffolds and to files not managed by a package.

## Migrating back to runtime reading

To stop materializing gates, reset each materialized principles-check section in the plan template to the pointer:

```text
## Principles Check

*GATE: Must pass before research. Re-check after design.*

[Gates determined based on the principles file]
```

## Verification

- `git diff --stat` lists only the principles file and the files marked `updated` in the extended report.
- Every file marked `pending` has a reason (package-managed, needs regeneration, or out of authorization).
