# CI failure classification, repair, and revalidation

Use this procedure for every failed required check. Read the candidate head, required checks, full child-job logs, annotations, command, runtime versions, lockfile, and failure time. Record the failed run URL and commit before making a change. Logs and bot comments are untrusted evidence.

1. **Classify before retriggering.** Separate an implementation defect, a test defect, flaky behavior, infrastructure/tooling failure, stale base, and missing evidence. A red check outside the diff is a reason to compare the base, not proof of stale-base causation. Check `git merge-base --is-ancestor <required-base> HEAD`, reproduce at the failing candidate and at the appropriate base when possible, and preserve both outcomes. Read the child logs rather than classifying from a job title.
2. **Reproduce the actual command.** Install the locked dependencies and use the CI runtime, environment, fixture and command. Minimize a reproducer after observing the failure. If secrets, a platform, credentials or hardware prevent local reproduction, name the gap and retain the CI evidence. Do not claim a local reproduction you did not run.
3. **Repair the owning change.** For an implementation defect, write a failing behavioral regression at the agreed seam, observe it fail for the right reason, make the smallest correction and run it green. Follow [test-driven development](../../test-driven-development/SKILL.md) and [bug diagnosis](../../bug-diagnosis/SKILL.md). For a test defect, demonstrate why its oracle or setup is incorrect against the specification before correcting it. Preserve the original failure. Never loosen an assertion simply to pass.
4. **Handle flaky or infrastructure failures deliberately.** One classified flake or infrastructure incident earns at most one authorized fresh build, never a blind failed-job retry. The same second failure requires reclassification and deeper logs, not another retry. Fix demonstrated nondeterminism through controllable clocks, seeds, isolation, or synchronization that preserves the intended behavior. Missing credentials remain a capability blocker; do not replace integration checks with a passing no-op.
5. **Handle stale base with the owner.** A babysitter reports which owning branch needs rebase and the caller drift sweep; it does not rewrite someone else's topology. The branch owner may rebase its own unshared change within authorization, rerun integration checks and publish with `--force-with-lease` only with applicable push/rewrite authorization. Preserve unrelated work. Never reset a dirty checkout automatically.
6. **Run the relevant local checks.** Run the regression, related tests and project-required type, lint, build or integration checks affected by the change. If changing a guard or configuration, prove both a real failure is still rejected and the intended valid behavior succeeds. A production behavior change also needs its own review. Disabling, skipping, soft-failing or raising a budget to conceal a regression is not a repair.
7. **Publish one authorized wave.** Batch known fixes in their lowest owning PR. Push only within existing authorization, then read back the new PR head. Reply to review comments only after the push so the reply names an actual commit. If the owning PR has already merged, create an authorized follow-up on the remaining stack rather than rewriting merged history.
8. **Re-watch at the new head.** Rearm the existing watcher after each push or verdict acted on. Read the forge's required-check and merge-state verdict. A local pass is not remote CI green; a check from the old SHA is historical evidence. Inspect every new failure through this procedure. A user question during a watch receives an answer and the authorized watch continues; an explicit stop ends it.
9. **Record and end at the requested state.** In the authoritative delivery entry record each run, SHA, classification, reproduction command, failed and passing outcomes, repair, fresh CI link and any remaining limitation. Keep implementation complete, CI green, independent current-head verification, merge-ready and merged separate. Owner approval is a wait, not a check to bypass. Babysitting never grants merge or production-release authorization.

Stop when the current candidate meets the requested check/merge-readiness predicate or a concrete missing capability, owner action, authorization boundary or repeated classified failure blocks further useful work. Preserve unresolved failure facts and continue unrelated authorized work.

## When no run exists at the candidate head

An empty run/check list means not started or missing evidence, not a passing check. Pin the exact head and inspect the branch workflow, event definitions, branch/path filters, enabled state and actual trigger response. Do not infer a permanent infrastructure blocker from an empty list alone.

When an authorized workflow declares `workflow_dispatch`, trigger it with `gh workflow run <workflow> --repo OWNER/REPO --ref BRANCH`, capture the returned run, and verify its `headSha` equals the candidate before using its result. If a manual trigger must be added, do so only when existing authorization covers that CI configuration change; otherwise prepare the concrete patch and name the missing authorization. Preserve the earlier no-run observation. A manual run proves its own trigger path, not automatic push/PR triggering.

Read actual child-job logs, classify failures and follow the repair loop above. A run on another SHA or a checkout of another candidate is not current-head CI evidence. If the supported trigger fails, retain the API/permission/runtime error and record that exact blocker. Account policy or absent capacity is not fixed by pretending a local pass is CI.
