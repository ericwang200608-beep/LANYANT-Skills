# Author extension and preset packages

Use this branch only when authoring or testing a toolkit customization package is the requested task. The bundled examples are authoring templates, not installed integrations and not complete business specifications. Follow [the customization contracts](../../delivery-planning/references/customization.md) for hooks, precedence and missing runners.

## Extension template

1. Copy [the extension starter](../assets/extension-template/) into an isolated project package directory. Retain the manifest, command, configuration, license, ignore rules, README example and changelog until the real package has replaced the corresponding sample content.
2. Customize `extension.yml`: schema version; lowercase hyphenated ID; name, semantic version and concise description; author; repository, homepage and license; category; read-only/read-write effect; toolkit compatibility; required or optional tools with versions; command names/files/descriptions and aliases; configuration name/template/description/required flag; hooks and their optional flag, prompt, description, priority and condition; tags and defaults. Confirm every declared path exists inside the package.
3. Replace `commands/example.md` with the real purpose, prerequisites, user input, configuration load and validation, main tool action, results processing, optional saved output, configuration reference, environment overrides, error handling and examples. Resolve command names to actual installed tools. A missing connector, credential, manager or hook runner is a blocker, not a successful simulated result.
4. Customize `config-template.yml`: connection URL and secret reference, project ID/workspace, feature flags, default labels/priority/assignee, field mappings, timeout/retry/cache settings and environment-variable overrides. Keep actual secrets out of packages, examples and logs; use ignored local overrides for developer-only values.
5. Replace README content using the complete example: features, installation, configuration, commands, prerequisites/outputs, configuration tables, environment overrides, workflow examples, troubleshooting, license/support and changelog. Update the actual copyright holder and release history rather than publishing placeholders.
6. Bind `<extension-manager>` to the target runtime's actual manager. In a disposable project test local development installation, command discovery, configuration precedence, declared prerequisites, hook dispatch, and one observable action with a real result. Check a real failing prerequisite too. If there is no manager, leave installation/registration and external action unverified; authoring files alone do not install an extension.
7. With explicit publication authorization, create the intended repository/release, verify the tagged archive and version compatibility, and follow the target catalog's submission path. Package, catalog, message and release permissions remain separate. Use [catalog maintenance](../../delivery-planning/references/community-catalog.md) only in an authorized catalog repository. Do not submit or publish from an authoring request alone.
8. For an existing catalog extension use [the complete lifecycle self-test](extension-selftest.md): exact-ID discovery, expected ordinary-install rejection for a discovery-only entry, trusted authorized URL installation, registration inspection and a terminal-style report with actual output.

## Preset scaffold

1. Copy [the preset scaffold](../assets/preset-scaffold/) and customize its ID, name, version, description, author/repository/license, compatibility, dependency declarations, tags and provided entries. Preserve `schema_version: "1.0"`.
2. Customize every provided `type`, `name`, `file`, description, optional replaced name and composition strategy. Document templates use lowercase hyphenated names; commands use the target runtime's namespaced IDs. A `script` entry is a capability declaration, not proof of a script dispatcher. Retain replacement, prepend, append and wrap semantics; scripts support only replacement and wrapping with their documented placeholder.
3. Fill the complete specification sample (created date/status, overview, requirements, acceptance), extension-report sample (summary, details and actions), core specification command, and extension-command customization (compliance before action and audit entries in output). A preset can override both core and extension commands only if the actual runtime registers those entries.
4. The shipped `preset.yml` uses JSON, a YAML subset, so the Python resolver can consume it without an optional parser. `preset.annotated.yml` retains the explanatory schema and composition examples for editing. Do not install both as separate presets. An ordinary YAML manifest additionally needs PyYAML.
5. Bind `<preset-manager>` to a real manager for local install/remove and command registration tests. For document-template resolution, copy the package into the isolated project's `.lanyant/presets/<id>` and run `python3 <suite>/project-environment/scripts/resolve_template.py <template-name> --json`. Check precedence, enable state and invalid-layer rejection. Resolution does not prove command registration.
6. Record scope, package version/digest, actual commands, before/after resolution, failures and results in the existing task entry. Remove a test install only within cleanup authorization. Release/catalog publication is a separate authorized action after replacing every sample field and proving installation.

## Self-test preset

[The self-test preset](../assets/preset-self-test/) retains five deliberately simple marked document templates (specification, plan, tasks, checklist, constitution), the specification override and the pre/core/post wrapper command. Use it only in an isolated resolver/registration test. Never substitute its placeholder requirements, task markers or principles for real project intent.

1. Copy the preset into an isolated `.lanyant/presets/self-test` and resolve all five template names. Each result must contain its own expected document structure and `preset:self-test` marker.
2. Verify removing or disabling the preset exposes the underlying template again. Preserve existing user files and state.
3. With a real command-registering manager, verify the specification override is selected, read user requirements, fill the specification, and retain the marker. Verify wrapping executes pre-logic, the actual resolved core, and post-logic exactly once and in order. A textual `{CORE_TEMPLATE}` placeholder is not execution evidence.
4. Keep local resolver evidence separate from manager lifecycle, command override and wrapper execution evidence. The suite includes no universal command/preset manager; record that gap accurately.
