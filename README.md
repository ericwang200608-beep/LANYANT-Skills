# LANYANT Skills

用于 AI 辅助软件开发与项目交付的技能库，覆盖想法评估、需求、设计、开发、验证、上线和维护。

本库包含 29 个 Skill。每个技能用 `SKILL.md` 定义工作方法，部分附带参考文档、模板和辅助脚本。你提供目标、业务决定和完成标准，代理读取适用技能后执行。

不需要记住全部技能，也不需要每次走完整套流程。从 [ask-eric](ask-eric/SKILL.md) 开始，或直接指定当前需要的技能。

## 安装与准备

### 1. 获取完整技能库

在终端进入你准备保存技能库的位置，再运行：

```bash
git clone https://github.com/ericwang200608-beep/LANYANT-Skills.git
cd LANYANT-Skills
```

如果已经下载或克隆过，直接使用已有目录。安装和更新时保留完整目录结构，技能会通过相对路径读取相邻技能。

在仓库根目录运行以下命令，可以重新统计技能数量：

```bash
rg --files -g SKILL.md -g '!**/node_modules/**' | wc -l
```

当前应输出 `29`。这条统计命令需要安装 `rg`，使用技能本身不要求先运行它。

### 2. 选择使用方式

| 方式 | 操作 | 适用情况 |
| --- | --- | --- |
| 直接读取 | 告诉代理技能库的绝对路径，要求读取对应 `SKILL.md` | 先试用，不修改技能安装目录 |
| 项目安装 | 将所有技能目录放入业务项目的 `.agents/skills/` | 团队在同一项目中使用 Codex |
| 用户安装 | 将所有技能目录放入 `~/.agents/skills/` | 个人在多个项目中使用 Codex |

Codex 支持上述项目、用户技能位置，也支持符号链接。安装发现与显式调用方式以 [Codex 官方技能文档](https://developers.openai.com/codex/skills) 为准。其他代理客户端需要按其自身规则配置技能位置。

直接读取时，把下面请求中的路径换成你本机的实际路径：

```text
业务项目位于 /absolute/path/to/my-project。
技能库位于 /absolute/path/to/LANYANT-Skills。
读取技能库中的 ask-eric/SKILL.md，并按照它处理我的任务。
本轮只检查现状和建议下一步，不修改业务项目。
```

预期结果是代理说明项目现状、当前缺口、适用技能和完成标准。它应读取真实文件，而不是仅凭技能名猜测流程。

如果希望代理帮助安装，可以发送：

```text
将 /absolute/path/to/LANYANT-Skills 中的全部技能安装到当前业务项目的
.agents/skills/。保留技能、参考文件、脚本、模板和许可证。
先检查同名技能与目录冲突，不覆盖已有版本。
如有冲突，先列出来源和差异，等待我决定保留哪个版本。
安装后检查技能是否被发现、相邻技能链接是否有效。
只做本地安装，不提交、不推送。
```

`refactoring`、`test-driven-development` 等通用名称可能与其他已安装技能重名。明确使用 LANYANT 版本或指定文件路径，避免调用到另一套流程。复制整个 `LANYANT-Skills` 文件夹到任意位置，不等于客户端已经自动注册其中的技能。

### 3. 打开要工作的业务项目

在代理客户端中打开业务项目，确认当前工作目录指向该项目。技能库提供工作方法，功能代码和项目记录写入业务项目的适当位置。

开始前提供已有需求、设计、任务、复现步骤或日志。代理应先读取这些材料，再问尚未解决的业务决定。账号、外部服务和运行工具按当前任务需要准备，不必提前安装所有可选依赖。

## 调用技能

### 用自然语言调用

已能发现技能时，直接描述任务并点名技能：

```text
使用 LANYANT 的 ask-eric，检查这个项目并判断下一步。
```

也可以直接点名：

```text
使用 LANYANT 的 bug-diagnosis，复现订单重复创建的问题，再修复并验证。
```

未注册或存在重名时，指定技能库绝对路径，让代理读取该版本。Codex CLI 和 IDE 扩展也支持通过 `/skills` 或输入 `$` 选择已发现的技能，例如 `$ask-eric`。这些是客户端中的调用方式，不是终端程序。

### 说明目标与完成标准

一个可执行的请求通常包含以下信息：

| 信息 | 示例 |
| --- | --- |
| 目标 | 修复重复点击入库后库存翻倍的问题 |
| 已知情况 | 当前库存 10，入库 5，快速点击两次后变成 20 |
| 完成标准 | 同一入库单重复提交只记账一次，不同入库单仍正常处理 |
| 证据 | 给出修复前复现、修复后相同步骤的结果及回归测试 |
| 边界 | 可以修改本地代码和运行测试，不提交、不推送、不部署 |

这些数字和业务规则只是示例。真实任务中的预期结果必须来自已经确认的要求。

可复制的请求模板：

```text
使用 LANYANT 的 ask-eric。

目标：<用户要完成的行为或要解决的问题>。
已知情况：<现象、文件、材料、复现步骤或任务链接>。
完成标准：<能判断通过或失败的结果>。
证据要求：<实际操作、测试输出、截图或前后测量>。
授权范围：<允许修改、提交、推送或部署到什么程度>。

先检查已有资料，复用已完成且仍有效的工作。
只询问影响业务含义、范围或授权的缺失决定。
在授权范围内完成工作，满足标准后结束。
```

同一聊天已经有这些信息时，后续可以直接说“继续”“按确认的范围实现”或“只修复这次发现的问题”。业务规则改变时，明确指出变更，代理应更新原有需求和受影响记录。

## 完整教程：交付一个库存管理功能

下面用“仓库人员登记入库，老板查看库存”的项目演示阶段衔接。已有项目从当前缺口开始，已有需求、方案和验证结果可以复用。

教程中的请求需要在能访问业务项目及 LANYANT 技能库的聊天中发送。根据实际项目调整范围和授权。

### 第一步：明确业务需求

发送：

```text
使用 business-discovery 梳理库存管理第一版需求。
仓库人员目前用 Excel 记录入库和出库，老板查看库存。
先阅读我提供的现有表格和流程说明，再分轮询问缺失的业务决定。
确定角色、数量含义、重复提交规则、第一版范围和验收场景。
本轮只完成需求，不开始开发。
```

你应看到已有事实、待定问题，以及带建议答案的业务问题。回答后，代理整理出一份权威需求说明，明确首版范围与验收条件。

如果不知道是否值得投入，先用 `idea-assessment`。如果某个流程仅靠描述难以判断，用 `workflow-prototype` 做临时演示，再把确认的结论写回需求。

### 第二步：确定技术方案

确认需求后继续：

```text
使用 technical-design，依据刚才确认的需求设计第一版。
先检查现有代码和环境，确定模块边界、数据模型、权限位置、接口及部署方式。
为关键技术未知项做必要调查或小型验证。
本轮交付技术方案和验证安排，不实现业务功能。
```

你应看到每个关键需求对应的实现方式、数据与接口约定，以及尚未解决的问题。小型内部工具不必为了凑文件创建没有用途的接口文档。

项目需要长期约束时，用 `project-principles` 记录真正采用的原则。技术取舍可以调用 `engineering-principles`，但不能把通用建议变成未经确认的业务承诺。

### 第三步：准备环境并安排第一批任务

发送：

```text
使用 project-environment 检查启动、测试、配置和测试数据是否齐全，补齐当前开发需要的基础。
再使用 delivery-planning，把已确认方案拆成可演示的业务批次。
第一批优先完成入库和库存查询，列出依赖、验收标准与检查方法。
允许本地配置和计划修改，不创建付费资源、不操作生产环境。
```

你应看到可执行的启动与检查入口，以及按依赖排列的任务。第一批应能演示完整行为，不应只完成一堆暂时无法验证的数据表和空页面。

### 第四步：实现第一批功能

发送：

```text
使用 feature-implementation 完成第一批任务。
按已确认规则处理权限、数量校验和重复提交。
关键业务规则按 test-driven-development 做失败到通过的验证。
运行功能并演示真实结果，更新现有任务记录。
允许修改本地代码和测试，不提交、不推送、不部署。
```

你应看到可运行的入库与查询行为、实际执行过的检查，以及失败或未验证项。编译通过不能代替完整流程验证。

任务确实可以独立拆分时，才考虑 `multi-agent-delivery`。功能明确且规模小，可以由一个代理完成。

### 第五步：验证这批功能

发送：

```text
使用 system-verification，依据已确认需求和第一批任务验证当前实现。
覆盖正常入库、无权限入库、非法数量、同一单据重试和库存查询。
记录候选版本、环境、预期结果、实际结果和未通过项。
本轮只验证，不修改代码、不发布审查意见。
```

你应看到验收场景逐项通过、失败或未验证的状态。发现问题后，可以另行授权修复，并重验受影响范围。

例如：

```text
修复本次验证中与第一批需求有关的问题，保留原失败事实。
只重验受影响场景和必要回归，不扩大功能范围。
```

当项目没有可重复的操作与验证入口时，用 `verification-harness` 建立它。若需要重点尝试打破高风险实现，用 `adversarial-review`。

### 第六步：按需要完成代码交付与客户验收

准备代码评审时发送：

```text
使用 pr-delivery，为当前已验证修改整理提交并创建 PR。
说明需求、变更范围和实际验证结果。
允许提交、推送并创建 PR，不合并、不部署。
```

客户准备试用时发送：

```text
使用 delivery-proof，在预发布环境安排仓库人员和老板按各自角色试用。
按已确认范围演练历史数据导入，核对数量和异常记录。
技术验证和客户确认分别记录，未确认项保持待办。
不操作生产数据。
```

PR 创建、检查通过和客户接受是不同状态。客户验收需要有权确认的人实际参与，代理不能替客户签字。

### 第七步：上线并交接

先准备发布：

```text
使用 project-release，准备当前已验收版本的正式发布步骤。
列出目标版本、环境、备份、数据切换、检查点和恢复方法。
本轮只准备方案，不执行生产发布。
```

确认方案后，单独说明发布的版本、环境和允许执行的动作。发布后按约定范围验证真实业务。

然后发送：

```text
使用 project-maintenance，准备仓库人员、老板和管理员的操作说明与交接。
明确账号资源、维护责任、监控、通知路径和后续问题入口。
区分材料已完成与培训效果已验证。
```

完成这些步骤的依据是实际产出和证据，不是聊天轮数。达到本轮约定结果后，就结束该轮工作。

## 已有项目的常用操作

以下请求都继承你已给出的授权。第一次执行时补充项目路径、材料与权限边界。

### 修复一个故障

```text
使用 bug-diagnosis。重复点击提交后出现两张相同订单。
先复现并缩小问题，再定位根因和修复。
用原来的步骤验证，并保留修复前失败、修复后通过的证据。
可以修改本地代码和测试，不提交、不推送。
```

### 改善性能

```text
使用 performance-investigation。用这份测试数据打开订单列表需要约 4 秒。
先测量基线和瓶颈，再优化。
在相同条件下报告前后耗时、重复测量情况和功能回归结果。
不要通过少返回数据或跳过处理来制造提速。
```

### 重构并保持行为

```text
使用 refactoring，把重复的价格计算归并到一个模块。
先记录当前行为，再调整结构，证明结果保持一致。
发现额外业务错误时单独报告，不改变本次行为约定。
```

### 审查当前分支

```text
使用 standards-spec-review，审查当前分支相对 main 的变更。
需求在项目现有说明中，以该文件为依据。
分别报告工程规范与需求符合性，只审查，不修改代码、不发 PR 评论。
```

把 `main` 和需求位置替换成真实基线与文件。若要包含未提交修改，明确说“连同暂存、未暂存和未跟踪文件一起审查”。

### 暂停与恢复

暂停时发送：

```text
使用 session-continuity，安全暂停当前工作。
保留已有修改，把完成情况、证据、未解决决定和恢复第一步写入现有任务记录。
不要删除包含未保存成果的工作目录。
```

恢复时发送：

```text
使用 session-continuity，从现有任务记录和实际代码恢复工作。
先说明哪些结果仍有效、哪些需要重验，再继续未完成部分。
不重复已完成且证据仍适用的工作。
```

### 安排多个代理

```text
使用 multi-agent-delivery，检查任务是否确实可以并行。
为独立任务指定工作目录、允许修改的文件、依赖和完成标准。
明确共享文件负责人，集成后验证完整行为。
允许本地修改和检查，不推送、不合并、不部署。
```

若需要无人值守执行，再写清停止条件、时间或资源预算，以及必须等待你决定的事项。技能本身不会创建调度器，也不保证关闭客户端后继续运行。

## 全部技能详解

下面逐一说明 29 个技能。标题链接用于本页查阅，每项的“操作手册”指向真实 `SKILL.md`。

### ask-eric

[操作手册](ask-eric/SKILL.md)

- 功能与作用：读取任务和项目现状，选择最短适用路线，协调阶段衔接，并判断是否已经完成。
- 使用时机：不知道用哪个技能、项目做到一半、任务跨多个阶段，或想知道下一步。
- 主要产出：当前状态、缺口、后续技能、交付内容和完成标准。已完成时建议停止。
- 示例：“使用 ask-eric，检查这个项目现在缺什么，在授权范围内继续完成。”

### engineering-principles

[操作手册](engineering-principles/SKILL.md)

- 功能与作用：将 24 条工程原则用于设计、实现、测试、测量和协作取舍。原则包括修复根因、先删减再增加，以及用执行证据证明结果。
- 使用时机：存在具体取舍，或用户点名某条原则。它提供通用判断方法。
- 主要产出：采取的决定、应用的原则及其对选择的影响。
- 示例：“应用 minimize-reader-load，判断这个模块怎样能减少调用方需要理解的内容。”

### project-principles

[操作手册](project-principles/SKILL.md)

- 功能与作用：建立或修改项目原则文档，维护质量门槛、治理、版本和变更影响。
- 使用时机：团队要明确长期约束，或现有规则需要正式修订。它维护项目自己的规则。
- 主要产出：有版本的原则文档、变更说明与待处理事项。同步其他模板属于显式选择的范围。
- 示例：“把金额计算采用精确数值类型写入项目原则，说明验证方式和版本变化。”

### idea-assessment

[操作手册](idea-assessment/SKILL.md)

- 功能与作用：依次收集想法、调查证据、定义问题、收敛方向并作出投入判断。
- 使用时机：还不确定值不值得做，或有人直接提出方案，但没有说明要解决的问题。
- 主要产出：各阶段材料、支持与反对证据，以及继续、需要澄清或停止的结论。
- 示例：“评估增加 AI 客服是否能解决当前客服压力，先不写需求、不开发。”

### business-discovery

[操作手册](business-discovery/SKILL.md)

- 功能与作用：通过材料、访谈和具体场景澄清范围、业务流程、术语、规则及验收条件。
- 使用时机：新项目、含糊需求、业务规则变更，或现有需求存在歧义。
- 主要产出：权威需求说明、范围、术语与决定、验收条件和未决问题。范围止于需求阶段。
- 示例：“把 Excel 库存流程整理成第一版需求，先查材料，再问缺失决定。”

### decision-mapping

[操作手册](decision-mapping/SKILL.md)

- 功能与作用：把大型不确定工作组织成决策地图，列出研究、原型、人工决定及其依赖。
- 使用时机：目标明确，但技术路径、迁移顺序或关键选择还不清楚，且需要跨会话推进。
- 主要产出：目的地、决策记录、可开展事项、阻塞关系和尚未明确的部分。默认以规划为主。
- 示例：“先梳理支付系统迁移需要解决哪些决策，明确后再安排实现。”

### workflow-prototype

[操作手册](workflow-prototype/SKILL.md)

- 功能与作用：制作临时可操作原型，观察业务逻辑、状态变化、交互和技术方案是否符合预期。
- 使用时机：流程难以在文字中判断，或需要对比不同设计方向。
- 主要产出：原型、试用场景、观察证据、反馈与结论。原型可运行不代表生产功能完成。
- 示例：“做一个可点击的请假审批原型，比较两种退回修改流程。”

### technical-design

[操作手册](technical-design/SKILL.md)

- 功能与作用：将业务需求落实为模块、数据模型、接口约定、部署方案及验证安排，调查技术未知项。
- 使用时机：需求已清楚，但实现方式或受影响模块的边界还没确定。
- 主要产出：技术计划、数据设计、必要接口契约、研究结论和验证指南。
- 示例：“根据库存需求设计数据表、权限实现位置和接口，本轮不写业务代码。”

### delivery-planning

[操作手册](delivery-planning/SKILL.md)

- 功能与作用：将需求和方案拆成可验证的业务任务与交付批次，并检查需求、计划和任务的一致性。
- 使用时机：方案已明确，需要安排实现；或现有任务过大、重复、遗漏和依赖混乱。
- 主要产出：有依赖关系的任务、批次、验收条件和首批建议。外部工单只在授权后发布。
- 示例：“把库存系统拆成三批，每批能演示一个完整业务结果。”

### project-environment

[操作手册](project-environment/SKILL.md)

- 功能与作用：检查并补齐项目结构、依赖、启动、自动检查、测试数据、环境配置和协作约定。
- 使用时机：开发前缺少工程基础，或已有项目无法可靠启动、测试和协作。
- 主要产出：可运行环境、可重复检查入口、配置说明和明确的环境缺口，也支持本地扩展与预设模板工作。
- 示例：“让新成员按说明就能启动项目并运行测试，补齐当前缺失配置。”

### feature-implementation

[操作手册](feature-implementation/SKILL.md)

- 功能与作用：按明确需求和任务实现完整行为，处理开发中遇到的相关故障，并实际运行和验证。
- 使用时机：业务目标明确，已有必要设计与执行条件，可以开始开发或修复限定问题。
- 主要产出：可运行修改、必要测试、执行证据和更新后的任务状态。
- 示例：“实现入库与库存查询，覆盖已确认的权限、数量和重复提交规则。”

### test-driven-development

[操作手册](test-driven-development/SKILL.md)

- 功能与作用：逐个行为写测试、观察正确原因导致的失败，再做最小实现并观察通过。
- 使用时机：业务规则、权限、金额、数量、状态、并发与数据一致性变更，以及有合适测试入口的故障修复。
- 主要产出：行为测试、失败到通过的结果、测试覆盖的边界及未验证项。通常配合开发或修复使用。
- 示例：“先用失败测试证明普通员工无法审批，再实现权限规则。”

### bug-diagnosis

[操作手册](bug-diagnosis/SKILL.md)

- 功能与作用：建立能识别目标故障的复现方式，缩小问题，验证假设，定位根因，再修复和清理临时诊断内容。
- 使用时机：报错、卡死、偶发失败、行为回退，或根因尚不明确。
- 主要产出：复现证据、原因、修复、回归结果及未验证限制。只要求诊断时止于诊断。
- 示例：“订单偶尔创建两次，先复现，再确认原因并修复。”

### performance-investigation

[操作手册](performance-investigation/SKILL.md)

- 功能与作用：测量基线、采集运行数据、定位性能瓶颈、优化并复测，解释数字代表什么。
- 使用时机：耗时、吞吐、内存、启动或渲染出现性能问题，或需要依据性能选择方案。
- 主要产出：工作负载、基线、瓶颈证据、前后测量与正确性检查。没有实际测量就不能宣称提速。
- 示例：“用这份数据测量订单查询，找到瓶颈并比较优化前后耗时。”

### refactoring

[操作手册](refactoring/SKILL.md)

- 功能与作用：通过重命名、提取、移动、归并和接口迁移改善结构，并在每步前后保持行为约定。
- 使用时机：行为已经正确，但代码难理解、重复或边界不清。
- 主要产出：结构修改、行为基线与等价验证。新功能或额外故障修复需要单独明确范围。
- 示例：“合并重复的价格计算，先记录现有输出，再证明重构后保持一致。”

### codebase-investigation

[操作手册](codebase-investigation/SKILL.md)

- 功能与作用：调查代码如何运行、历史上为什么这样设计，研究技术资料，或用教学方式解释一个主题。
- 使用时机：接手陌生模块、查历史原因、研究技术选择，或需要更清楚的解释。
- 主要产出：带证据的说明、推断与未知项；研究模式可写笔记，教学模式可维护学习资料。业务代码保持只读。
- 示例：“解释订单状态如何变化，以及当初为何采用现在的设计，暂不修改。”

### standards-spec-review

[操作手册](standards-spec-review/SKILL.md)

- 功能与作用：从工程规范和需求符合性两条轴审查指定基线之后的变更，使用独立上下文分别给出发现。
- 使用时机：分支、PR 或未提交修改需要审查。
- 主要产出：两条审查结论、问题位置、规则或需求依据、范围和独立性说明。静态审查不能代替运行验证。
- 示例：“审查当前分支相对 main 的修改，分别检查规范和需求，只报告不修复。”

### adversarial-review

[操作手册](adversarial-review/SKILL.md)

- 功能与作用：主动尝试打破实现，保留能复跑证明的问题，也支持影响范围、注释及自动审查意见核实。
- 使用时机：高风险变更、对实现存疑、边界条件复杂，或审查意见存在争议。
- 主要产出：验证成立的问题、复现证据及被排除的发现。默认只审查，修复和删除注释需有相应授权。
- 示例：“尝试用并发与重复请求打破退款逻辑，只报告能证明的问题。”

### system-verification

[操作手册](system-verification/SKILL.md)

- 功能与作用：对照需求、设计和任务检查当前实现缺口，并实际执行关键系统场景。
- 使用时机：一批功能完成、修复后复查，或要判断当前系统是否满足约定要求。
- 主要产出：工程规范与需求符合性结论、场景运行结果、剩余事项及证据。独立上下文缺失时必须说明限制。
- 示例：“验证创建订单、取消和退款的完整流程，对每个验收项记录结果。”

### verification-harness

[操作手册](verification-harness/SKILL.md)

- 功能与作用：建立并维护项目专用的可重复运行验证技能、功能地图和检查入口；必要时进行形式化模型检查。
- 使用时机：缺乏可靠验证方法、检查随代码变化失效，或并发与重试性质需要模型验证。
- 主要产出：执行过的验证流程、证据和覆盖范围；形式化分支可提供模型与反例。有限模型通过不等于整个系统正确。
- 示例：“建立可重复执行的订单验证，并检查并发扣库存是否可能出现超卖。”

### pr-delivery

[操作手册](pr-delivery/SKILL.md)

- 功能与作用：整理分支和提交、编写并创建 PR、处理 CI 与审查意见，并在授权后推进合并。
- 使用时机：代码准备进入评审，PR 检查失败，或需要处理评审与依赖 PR。
- 主要产出：PR、实际检查状态、处理结果和剩余阻塞。创建 PR、合并和生产部署是独立动作。
- 示例：“整理提交并创建 PR，修复 CI 失败和审查问题，暂不合并。”

### delivery-proof

[操作手册](delivery-proof/SKILL.md)

- 功能与作用：在预发布环境用客户数据和实际角色流程验证交付，必要时演练历史数据导入并核对结果。
- 使用时机：准备客户试用、业务验收或正式数据切换前演练。
- 主要产出：场景证据、数据核对、客户确认和剩余问题。技术通过不能代替客户确认或生产授权。
- 示例：“用客户库存数据演练导入，让仓库人员完成业务验收并核对数量。”

### project-release

[操作手册](project-release/SKILL.md)

- 功能与作用：准备并执行发布、试点、业务切换、备份、代码回滚和数据恢复，在上线后检查真实使用。
- 使用时机：预发布验收已完成，需要正式上线或执行已有恢复程序。
- 主要产出：生产版本与实际状态、发布记录、恢复方案和验证结果。生产执行需要明确目标与授权。
- 示例：“先准备版本发布和恢复步骤，获准后切换并验证关键业务。”

### project-maintenance

[操作手册](project-maintenance/SKILL.md)

- 功能与作用：完成按角色培训、管理员与资源交接、监控验证、维护安排，以及后续事故和需求分流。
- 使用时机：上线前准备培训交接，或上线后需要持续支持。
- 主要产出：操作说明、培训结果、资源责任、监控证据和后续问题入口。材料完成与用户会操作分开判断。
- 示例：“准备管理员培训和运维交接，验证访问权限、告警路径和维护责任。”

### issue-triage

[操作手册](issue-triage/SKILL.md)

- 功能与作用：核实收到的问题、外部 PR 和报告，查重分类，整理标签、缺失信息与可接手任务。
- 使用时机：反馈入口杂乱、工单描述不清、报告真实性待确认，或需要建立受控的持续收集流程。
- 主要产出：分类结论、核实结果、责任去向和执行简报。外部标签、工单及消息修改需要授权。
- 示例：“整理这些用户反馈，合并重复项，把确认的问题整理成可执行任务。”

### multi-agent-delivery

[操作手册](multi-agent-delivery/SKILL.md)

- 功能与作用：协调任务依赖、独立工作目录、共享文件负责人、并行执行、集成、独立验证和有界运行。
- 使用时机：工作有真实可拆分部分，涉及多代理、多分支、多 PR，或需要独立方案比较。
- 主要产出：任务分配、集成成果、验证证据和阻塞状态。子任务通过不能代替集成后验证。
- 示例：“把独立模块分给多个代理，明确允许修改的文件，集成后验证完整行为。”

### session-continuity

[操作手册](session-continuity/SKILL.md)

- 功能与作用：安全暂停、核对并恢复已有成果、回顾进展，或把工作交接到其他会话和执行者。
- 使用时机：隔天继续、上下文变长、换工作目录或换人接手。
- 主要产出：目标、范围、已验证成果、未决事项、证据位置与准确恢复点。原授权边界继续保留。
- 示例：“从现有任务记录恢复工作，核对真实代码，只继续剩余部分。”

### technical-writing

[操作手册](technical-writing/SKILL.md)

- 功能与作用：编写或修改技术文档、方案、操作指南、PR 和提交文案，也支持重述目标与简化解释。
- 使用时机：需要让特定读者理解技术内容或按说明完成操作。
- 主要产出：术语一致、事实可核对、适合读者的文档。交付草稿不等于允许发送或发布。
- 示例：“把部署笔记整理成新成员能按步骤操作的指南，核对命令和路径。”

### process-improvement

[操作手册](process-improvement/SKILL.md)

- 功能与作用：根据执行证据复盘，把重复问题转成结构、类型、工具或检查，也能维护代理指令、提示词和技能。
- 使用时机：同类错误反复出现、希望调整协作方式，或需要创建和修改 Skill。
- 主要产出：有依据的改进建议及获准修改后的验证结果。复盘建议不会自动扩大修改范围。

### 审查与验证的区别

| 技能 | 主要回答的问题 |
| --- | --- |
| `standards-spec-review` | 这次修改是否符合工程规范和原始需求？ |
| `adversarial-review` | 哪些异常或边界操作能触发实际缺陷？ |
| `system-verification` | 当前这一批功能运行后是否达到约定标准？ |
| `verification-harness` | 怎样建立以后可以重复执行的验证方法？ |
| `delivery-proof` | 客户用真实角色和数据能否完成业务，并确认接受？ |

其他容易混淆的组合：

- `idea-assessment` 判断是否值得投入，`business-discovery` 明确决定做的业务要求。
- `decision-mapping` 拆未解决的决策，`delivery-planning` 拆已明确的执行工作。
- `engineering-principles` 提供通用取舍方法，`project-principles` 维护项目已采用的约束。
- `feature-implementation` 增加行为，`bug-diagnosis` 修正故障，`refactoring` 保持行为并调整结构。
- `pr-delivery` 推进代码评审与合并，`project-release` 处理正式发布与业务切换。

## 检查结果与结束任务

阅读代理交付时，核对以下内容：

1. 完成了什么用户行为，是否仍在约定范围内。
2. 对哪个版本、哪个环境实际运行了哪些检查。
3. 预期与实际结果是什么，有没有失败、模拟或未验证部分。
4. 当前任务记录是否反映真实状态，证据路径是否可用。
5. 是否还存在影响本轮完成标准的阻塞。

以下状态分别记录，不能互相代替：

| 状态 | 需要的依据 |
| --- | --- |
| 实现完成 | 对应修改已经存在 |
| 技术验证通过 | 当前候选版本完成所需检查与实际场景验证 |
| 客户验收通过 | 有权确认的人接受约定结果 |
| PR 已合并 | 目标分支中存在对应合并结果 |
| 发布已授权 | 对指定版本、环境和操作有明确许可 |
| 上线验证通过 | 实际生产环境中的关键业务完成检查 |
| 交接完成 | 使用、管理、资源和维护责任完成约定交接 |

约定结果已经完成、必要检查通过、阻塞解决或有明确处置后，就结束当前工作。未来环境验证、后续业务批次和可选改进单独保留，不重复开展已经有效的检查。

## 依赖、权限与使用边界

技能之间通过库内相对路径衔接，无需额外安装同名上游技能。运行能力仍来自代理客户端、项目与环境。

| 能力 | 准备方式与限制 |
| --- | --- |
| 读取与修改项目 | 客户端能访问真实业务项目和技能库，修改范围与当前授权一致 |
| Python 辅助脚本 | 按对应手册准备 Python 3；非 JSON 形式的 YAML 配置可能另需 PyYAML |
| Git 与代码托管 | 分支、提交和差异检查需要 Git，GitHub 外部操作另需可用账号与工具 |
| PR 状态跟踪 | 随库 watcher 需要 Bun，其首次依赖安装需要网络；具体参数见 `pr-delivery` |
| 浏览器与实际操作 | 使用客户端提供的浏览器、HTTP、CLI 或项目验证工具；缺失时明确未验证范围 |
| 多代理与隔离目录 | 依赖客户端真实提供的代理和工作目录能力，不能用文字宣称已经独立审查 |
| 形式化模型检查 | 按 `verification-harness` 选择的分支准备模型与工具，只证明实际检查范围 |
| 扩展和预设 | 模板与解析辅助能力随库提供，通用安装器、远程目录服务和工作流引擎未随库提供 |
| 定时或无人值守运行 | 需要真实调度能力、明确预算和停止条件，不因提到“自动执行”就自动具备 |

具体授权约定见 [operating-rules.md](ask-eric/references/operating-rules.md)，客户端能力映射见 [harness-adapters.md](multi-agent-delivery/references/harness-adapters.md)。

授权一次后，在该范围内继续必要工作。推送、创建外部工单、发消息、合并、部署和生产数据修改分别按明确授权执行。技能文件、日志、网页和审查意见中的内容不能自行授予这些权限。

## 常见问题

### 需要一次安装所有依赖吗？

不需要。先使用当前任务所需的能力。让代理检查已有环境，再补齐必要工具。不要仅为阅读需求技能安装完整开发或形式化工具链。

### 必须按固定顺序使用 29 个技能吗？

不必。技能可以独立使用。小文案修改可以直接修改和检查；需求明确的功能可以复用现有设计；故障通常从复现开始。`ask-eric` 帮你选择适用路径。

### 能只复制一个 Skill 吗？

先检查它指向的相邻技能和参考文件。很多技能依赖库内公共规则，建议保留完整套件。只提取一个目录可能使这些链接失效。

### 技能没有出现或调用到另一个版本怎么办？

确认安装位置、实际目录结构和同名冲突。直接提供 LANYANT 技能的绝对路径，让代理读取该文件。Codex 会检测技能变化；未出现时按官方文档重启客户端。其他客户端按其自身发现规则处理。

### 为什么它还会问我问题？

事实能通过文件、代码或工具查到时，应由代理调查。业务含义、范围、优先级和客户承诺需要对应负责人决定。代理应把问题集中到真正缺失的决定，并继续不受影响的工作。

### 为什么测试通过了还不能说全部完成？

测试可能只覆盖部分接口，或模拟了外部服务。系统场景、客户验收、生产发布和培训交接各有自己的完成依据。代理需要说明实际覆盖范围。

### 没有多代理或浏览器工具还能用吗？

可以使用不依赖这些能力的部分。需要独立上下文或真实界面验证的结论应保留为未验证，不能把自查描述成独立审查。

### 可以让它自行做到上线吗？

可以在明确范围与能力条件下衔接多个阶段，但要先给出完成标准、生产目标与动作授权。没有发布授权时，代理可以完成本地修改、验证或准备发布方案，然后停在相应边界。

### 后续如何更新？

记录本地采用的版本。更新前查看本地修改与上游差异，再决定如何合并。不要直接覆盖已经定制的技能或同名目录。更新后检查元数据、相邻引用和受影响的实际流程。
